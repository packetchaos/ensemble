1Summary for the CISO

navi Ensemble turns the vulnerability, asset and tag data your team already pulls from Tenable with navi into specialist views: actively exploited exposure (CISA KEV), asset truth, scan coverage, ownership and SLA, certificates and post-quantum readiness, OT/IoT, AI exposure, compliance and more. Each specialist can also write its findings back to Tenable as tags or Asset Criticality Rating (ACR) changes, so Tenable One and your other tooling see the same picture.

The design choices that matter for risk:

  • It is a local tool, not a service. One Python process on an analyst's machine or a jump box, listening on 127.0.0.1 only. There is no vendor cloud, no telemetry and no account to create.
  • It reads a local copy, not your tenant. Analysis runs against navi.db, a SQLite snapshot that navi syncs from Tenable. The Ensemble opens it read-only.
  • Every change is opt-in, twice. Writes need a server-side gate switched on and a per-action confirmation. Email, remote command execution and scan launch each need a further, separate gate. Changes are refused from any browser that is not on the console's own machine.
  • Findings are explainable. Detection and scoring are SQL and rules. Every number opens the exact assets or findings behind it. An AI model, if you configure one, only helps write queries and summaries, and what it proposes is shown before it runs.
  • You control what leaves. The only required external connection is Tenable's API through navi. Model providers, public threat feeds and Google Fonts are listed in the SBOM with exactly what crosses.

2Architecture

Components

ComponentWhat it isSecurity-relevant facts
Web serverapp_stdlib.py, Python standard library http.server. FastAPI and Flask variants exist as opt-in alternatives. One policy module (core/security.py) applies to every request on all three. Binds 127.0.0.1 by default. Runs with umask 077.
Dispatchercore/launcher.py routes each request to a specialist action. Declares which actions write (served to the pages), refuses destructive actions from non-loopback browsers, applies tag scopes and budgets.
Specialists43 modules under agents/ — Python plus one HTML page each. Read navi.db with SQL and rules. Results are cached on the server, keyed to the exact navi.db file.
Data layercore/db.py over navi.db. Opens with mode=ro plus PRAGMA query_only. SQL written by a person or a model runs under a SQLite authorizer that denies navi's credential tables (keys, smtp, ssh, resend).
navi CLIThe open-source Tenable CLI, called as a subprocess. Owns the Tenable API keys, SMTP and SSH settings. Its binary path and working directory cannot be set from the browser.
Browser UIFirst-party HTML, CSS and JavaScript under web/ and agents/. No third-party scripts or stylesheets (enforced by a test). Every value placed into a page is HTML-escaped.
MCP serverhounds_mcp.py, optional, exposes the same engines to Claude and other MCP clients. Stdio by default. Its HTTP mode has no authentication, so it refuses a non-loopback host unless explicitly allowed.
Local stateCaches, Tagging log (tag_jobs.db), job audit logs, dashboards, Automation Station policies. Written 0600 (folders 0700). All git-ignored. None of it is sent anywhere.

5How changes are gated

Nothing is written to Tenable, mailed or run on a host unless every layer below agrees. Turning a gate off never needs a confirmation; turning one on from the Settings page needs a browser on the console's machine.

CapabilityGate 1Gate 2Gate 3Also required
Tags, ACR, removalsNAVI_ALLOW_WRITES=1confirm: true on the action—Browser on the console's machine. A dry-run preview is shown first.
EmailNAVI_ALLOW_WRITES=1NAVI_EMAIL=1confirm: trueSMTP configured in navi out-of-band. Plain recipients, single-line subjects.
Remote command executionNAVI_ALLOW_WRITES=1NAVI_REMOTE_CODE_EXECUTION=1confirm: trueSSH configured in navi. One host at a time. The highest-risk capability.
Scan launchNAVI_ALLOW_WRITES=1NAVI_SCAN_LAUNCH=1confirm: trueA review step before launch.
Strict confirmation. confirm must be the JSON value true. The strings "true", "1" or the number 1 are refused, so a script or a model can't confirm by accident. Gates can also be switched on with an empty file in the repo root (ALLOW_WRITES and similar). Those files only count when they belong to the user running the server, are not symlinks and can't be written by anyone else, and startup says when one is in use.

6Use of AI

Where a model is used

  • Turning a plain-English request into a query, tag rule or plan.
  • Plain-English summaries and briefings.
  • Suggesting tag names and groupings.

In each case the query, rule or plan is shown before anything runs, and any write still passes every gate in section 5.

Where a model is never used

  • Detecting exposure — every specialist is SQL and rules.
  • Scoring and prioritising.
  • Deciding to write, mail or run anything.
  • Holding or seeing your Tenable API keys.

The same navi.db always gives the same answer.

7Common questions

Does it need inbound firewall rules or a public endpoint?
No. By default it listens on 127.0.0.1 and nothing outside the machine can reach it. Shared use is an explicit opt-in (HOUNDS_BIND) that adds a per-launch access token, and even then changes are only accepted from the console's own machine.
What Tenable permissions does it need?
Whatever the navi API keys have. For a read-only deployment, give navi keys from a Tenable user with read access and leave the write gate off; the console still works fully for analysis. Tagging and ACR changes need a role that can manage tags and assets. Scan launch needs scan permissions. Least privilege in Tenable is your strongest control.
Where are credentials stored?
Tenable keys, SMTP and SSH settings are stored by navi (in navi.db), not by the Ensemble. Model API keys come from the environment, .env, or the Settings config file (hounds.config.json, chmod 600, plain text, git-ignored). Choose Ephemeral storage or HOUNDS_CONFIG=off if keys must never be written to disk. Keys are never sent to the browser.
Could someone use the console to read the API keys out of navi.db?
Not through the console. SQL typed by a person or proposed by a model runs under a SQLite authorizer that denies the keys, smtp, ssh and resend tables, and those values are also on the response scrub list. Anyone with file access to navi.db on the machine can read it directly, so protect that file like any credential store.
Can it change my Tenable tenant without someone noticing?
Not by default: writes are off. With writes on, each change needs an explicit confirmation from a browser on the console's machine, shows a preview first, and is recorded in the Tagging log and job logs. Scheduled runs (Automation Station) must be armed deliberately and are subject to the same gates.
Does any of our vulnerability data go to an AI company?
Only if you configure a hosted model, and then only the prompts for the plain-English features you use. Run with no model, or with Ollama on the same machine, and nothing goes to a model provider.
Is there telemetry or phone-home?
No. The external connections are the ones in section 3. The only one made on every page load is Google Fonts, by the browser, which carries no application data and can be blocked.
How is remote command execution controlled?
It is off by default and needs three switches (writes, remote execution, confirm), a browser on the console's machine, and SSH configured in navi. It targets one Linux host per call. Its destructive-command list only warns and forces an extra confirmation; it is not a sandbox, so treat this capability as privileged access and enable it only where you would allow SSH from that machine.
What happens to navi.db and the caches?
They stay on the machine. navi.db is a snapshot of your tenant and should be treated as sensitive. The console only reads it. Caches and logs are written with owner-only permissions and are excluded from git.
How has it been tested?
112 automated test suites ship with the code, including server security, write-gate, export, scale and SBOM-freshness tests. Release 2.44.521 was a full security sweep (bandit, semgrep, pip-audit, detect-secrets and three manual reviews, with every finding independently reproduced before and verified after fixing). Release 2.44.529 acted on three independent reviews: loopback-only changes, hardened gate files, one reference server, and no silently ignored errors.
Can I verify what is installed?
Yes. The committed SBOM lists declared requirements; Settings ▸ Software bill of materials ▸ This install, or python3 tools/sbom.py --installed --stdout, produces an exact inventory of the running install. python3 check_writes.py shows which gates the server resolved and why.
Who supports it?
navi Ensemble and navi are open source under their own licenses, not a commercial Tenable product, and come without warranty. Review them as you would any open-source tool you run with production credentials.

8Known limitations

These are known gaps rather than defects. Plan compensating controls where they matter to you.

LimitationImpactCompensating control today
No SSO, role-based access or two-person approvalAnyone who can use the console on its machine has its full capability, within the gates.Run per analyst, keep writes off on shared hosts, use HOUNDS_REQUIRE_TOKEN=1, and scope navi's Tenable role.
Audit logs are localNo built-in forwarding to a SIEM.Collect logs/navi-jobs/ and tag_jobs.db with your log agent. Tenable's own audit log records the API calls navi makes.

10Deployment checklist

  1. Run it on a managed analyst workstation or a hardened jump box, as a dedicated non-admin user.
  2. Give navi Tenable API keys from a least-privilege user. Read-only if you only need analysis.
  3. Keep the default 127.0.0.1 bind. If you must share it, set HOUNDS_REQUIRE_TOKEN=1 and put it behind your own TLS and access controls.
  4. Leave NAVI_ALLOW_WRITES off until a named owner needs tagging or ACR changes. Enable email, remote execution and scan launch only where they are needed, and only on that machine.
  5. Choose a model provider that matches your data policy: none, Ollama, Bedrock in your account, or a hosted provider under your terms.
  6. Store model keys in the environment or use Ephemeral storage; protect navi.db as a credential store and tenant snapshot.
  7. Forward logs/navi-jobs/ and the Tagging log to your SIEM, and watch Tenable's audit log for the navi API user.
  8. Keep the full-disk encryption and endpoint protection you require for any host that stores vulnerability data.
  9. Record the installed SBOM (--installed) with each upgrade, and review the CHANGELOG before upgrading.
